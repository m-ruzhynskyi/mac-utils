# Протокол трансляции экрана: mu-share-1 и mu-share-2

Как устроено на самом деле (relay `relay/src/index.js`, `limits.js`, `auth.js`; Mac `Features/ScreenShare/*`; страница `relay/src/index.html`).
Дизайн и обоснования: `.audit/auth-design.md`. Правила версий протокола: [VERSIONING.md](VERSIONING.md), раздел 3.

## 1. Кратко

- У каждого пользователя постоянный 10-значный ID. Это «комната» на relay: Durable Object `idFromName(<ID>)`.
- **mu-share-1** — прежний протокол, без ключей. ID никак не проверяется.
- **mu-share-2** — тот же поток плюс проверка устройства ключом (challenge/response): Ed25519 у приложений, P-256 у страницы relay (§3.1):
  - первый ключ, прошедший проверку на ID, становится его **владельцем**;
  - вести трансляцию на этом ID может только владелец;
  - ID зрителя тоже сверяется с владельцем (`idVerified`).
- Кадры и звук relay не разбирает и не хранит. Сквозного шифрования нет (TLS только до relay).

## 2. Токен клиента и `GET /version`

Каждый запрос приложения несёт заголовок `X-MacUtils-Client`:

| Токен | Кто шлёт | Что значит |
|---|---|---|
| `mu-share-1` | Mac до линии 1.5, Mac без доступа к Связке ключей, Windows без ключа, любой клиент на relay без v2 | Без проверки устройства; с `auth=v2` в адресе — как `mu-share-2` (ключ страницы, §3.1) |
| `mu-share-2` | Mac 1.5+ с ключом в Связке ключей; Windows с ключом в `safeStorage` (W1; в 1.1.12 выпущен, в 1.1.13 откачен — Windows сейчас ходит по `mu-share-1`) | Проверка устройства (если `AUTH_MODE` не `off`) |

Без заголовка или с неизвестным значением: страница-лендинг, 403 на `/room/*` и `/status`.

**`mu-share-1` + `auth=v2` в адресе** (`/room/<ID>?…&auth=v2`, `/room/<ID>/host-check?auth=v2`) relay понимает как `mu-share-2`: так проверку ключом просит страница с собственным ключом (§3.1), когда приложение ставит `mu-share-1` и заголовок не меняет (клиент для Windows). В `required` такой клиент тоже пускается; в `off` параметр игнорируется. Старый relay параметр не знает и идёт по mu-share-1.

**`GET /version`** — без заголовка, `cache-control: no-store`:
```json
{ "commit": "<RELAY_COMMIT или dev>", "protocols": ["mu-share-1", "mu-share-2"], "auth": "optional" }
```
- В `required` `protocols` = `["mu-share-2"]`.
- **Правило для клиентов:** `mu-share-2` ставится **только** если он есть в `protocols`. Нет ответа, 404 или HTML (relay до v2) → `mu-share-1`.
- Mac так и делает (`ShareRelay.capability`) и кэширует ответ по host:port. Неудачный запрос не кэшируется. При ответе 403/426 на подключение кэш сбрасывается и `/version` запрашивается заново.
- Windows обязан делать так же (контракт W1, `.audit/auth-design.md` §2.3).

## 3. Хост (ведущий)

`wss://<relay>/room/<ID>?role=host`

**mu-share-2:**
1. relay → `{"type":"challenge","v":2,"nonce":"<base64url, 32 байта>"}`
2. хост → `{"type":"auth","v":2,"alg":"ed25519","pub":"<b64u 32 байта>","sig":"<b64u 64 байта>"}`
   - подпись по строке `mu-share/v2\nhost\n<ID>\n<nonce>`;
   - `<ID>` клиент подставляет сам, из адреса, куда подключался.
3. Успех → `{"type":"authed","v":2,"fp":"a1b2-c3d4-e5f6-0718","claimed":true|false}`
   - `claimed:true` — ID только что закреплён за этим ключом.
4. Ошибка → `{"type":"error","code":"…","message":"<текст по-русски>"}`, затем закрытие с кодом из §6.

До `auth` сокет хостом не считается:
- не получает запросов;
- его кадры и команды отбрасываются;
- обрыв не запускает grace.

Хост с ключом владельца **вытесняет** прежние подключения хоста на этом ID: своё старое окно → `replaced` 4409, хост без ключа → 4409 без `error`.
- Зрители, которых пустил другой ключ или хост без ключа, получают `ended`. Это верно и во время grace.
- Зрители, пущенные этим же ключом, остаются.

**mu-share-1:** как раньше, без challenge. Если у ID уже есть владелец — HTTP 409 `id-claimed` (кроме `AUTH_MODE=off`).

### 3.1. Ключ страницы relay (`alg: "es256"`)
Приложение без своего ключа (клиент для Windows сейчас, браузер) получает ключ от самой страницы:
- P-256 ECDSA через WebCrypto (Ed25519 в WebCrypto Chromium 130 нет — `NotSupportedError`); приватная часть неэкспортируемая, хранится в IndexedDB сайта relay (`mu-device-key`), создаётся один раз;
- `auth`: `{"type":"auth","v":2,"alg":"es256","pub":"<b64u 65 байт: 04‖x‖y>","sig":"<b64u 64 байта: r‖s>"}`, хеш SHA-256, строки подписи те же;
- отпечаток — как у Ed25519: первые 8 байт SHA-256 сырых байт ключа;
- страница подписывает вход ведущего и зрителя; подписанный `/status` — только ключом приложения (Ed25519);
- ключ страницы используется и как ведущий: иначе ID, закреплённый ею при просмотре, нельзя было бы занять по mu-share-1;
- ключ недоступен (нет API, IndexedDB закрыт или не ответил за 3 с, самопроверка подписи не сошлась) — страница работает по mu-share-1, как раньше.

Mac принимает такой `pub` в `request` (`ShareHistory.isPublicKey`: 43 символа Ed25519 или 87 символов P-256 с точкой на кривой) и проверяет подписи P-256 через CryptoKit (`ShareIdentity.verify`). Mac до этой версии видит такой запрос как `auth:"none"` (вопрос без «Всегда»).

**«Сменить ID» / «Получить новый ID»:** хост с ключом шлёт `{"type":"release"}`.
- relay стирает владельца, зрители получают `ended`, сокет закрывается 1000.
- Mac после этого создаёт новый ключ и новый ID.

**Grace:** обрыв не по «Стоп» (код ≠ 1000) — зрители получают `reconnecting` и ждут 45 с.
- Вернуть комнату может только хост, прошедший проверку ключом владельца (или legacy-хост, если ID свободен).
- Вернулся — зрители получают `resumed`. Не вернулся — `ended`.

## 4. Зритель

`wss://<relay>/room/<ID>?role=viewer&viewer=<свой ID>&name=<имя>&h264=1`

**mu-share-2:**
1. relay → `{"type":"challenge","v":2,"nonce":"…","rid":"<uuid>","hostKey":"<pub владельца|null>","hostFp":"<fp|null>"}`
   - `viewer` должен быть **ровно** 10 ASCII-цифр, иначе `id-format`.
2. Зритель сверяет `hostKey` с запомненным для этого ID (Mac: `ShareHistory.hostKey(for:)`). Если не совпало, соединение не продолжается, пользователю показывается «Ключ изменился».
3. зритель → `auth` с подписью по `mu-share/v2\nviewer\n<ID комнаты>\n<свой ID>\n<rid>\n<nonce>`
4. relay → `{"type":"waiting","v":2,"rid":"…"}`, хосту:
   ```json
   {"type":"request","v":2,"viewer":"…","name":"…","rid":"…","auth":"key","pub":"…","fp":"…","idVerified":true,"self":false}
   ```
   - `idVerified` — ID зрителя закреплён за этим же ключом (relay проверяет и при необходимости закрепляет его в комнате этого ID);
   - `self` — это ключ владельца комнаты (окно «сам себе»).
5. хост → `{"type":"accept"|"decline","viewer":"…","rid":"…","name":"<имя ведущего>","hostSig":"…"}`
   - для хоста с ключом `rid` обязателен;
   - `hostSig` — подпись хоста по `accept\n<ID комнаты>\n<pub зрителя>\n<rid>`. Зритель сверяет её с `hostKey`, отсутствие допустимо (старый хост).
6. relay → `{"type":"accepted","name":"…","hostSig":"…"}` / `{"type":"declined"}`.

До `auth` зритель может слать только `auth` (один раз) и `heartbeat`. Повторный `auth` закрывает сокет кодом 4400.

**mu-share-1:** сразу `waiting` без challenge. Хосту уходит:
- `{"type":"request","viewer","name","rid"}`, если хост без ключа (как раньше);
- то же плюс `"v":2,"auth":"none"`, если хост с ключом.

### Правило решения у хоста (Mac и страница)
1. `auth:"key"` и `self` → принять.
2. `auth:"key"`, `idVerified`, и пара «ID + ключ» в доверенных → принять. Без `idVerified` запись «доверен» не действует: ID закреплён за другим устройством.
3. Иначе — окно запроса с отпечатком и предупреждениями:
   - «ID не подтверждён»;
   - «старая версия, личность не проверена» для `auth:"none"`;
   - «ключ изменился».

   «Всегда разрешать» есть только при `auth:"key"` и подтверждённом ID.

Доверенные по ID из старых версий (без ключа) на первый запрос с ключом получают окно «подтвердите один раз».

### Прочие сообщения (как и в mu-share-1)
- `heartbeat` в обе стороны;
- `viewers {count, list[{id,name,h264, fp?, auth?}]}` хосту;
- `cancelled {viewer, rid}` хосту;
- `reconnecting`, `resumed`, `ended` зрителям;
- от одобренного зрителя: метки `ping`/`stroke` и `game` (relay пересобирает их из проверенных полей, `from`/`name`/`fp` ставит сам);
- двоичные кадры: первый байт — тип (1 JPEG, 2 PCM, 3 H.264).

Новые типы и поля протокола только добавочные: старые клиенты их не получают или игнорируют.

## 5. `/status` — кто в эфире

| Запрос | Кто может | Что делает |
|---|---|---|
| `GET /status?ids=a,b,…` | любой клиент с токеном | Только 10-значные ID, не больше 20. В `required` → 426 |
| `POST /status`, тело `{"v":2,"id":"<мой ID>","pub":"…","ts":<мс>,"ids":[…],"sig":"…"}` | владелец `id` | Подпись по `mu-share/v2\nstatus\n<id>\n<ts>\n<ids через ,>`, свежесть `ts` ±120 с, `ids` ≤ 20 (10 цифр). **Только чтение:** свободный ID не закрепляется. Ключ не владелец → 403 `id-claimed`; у ID нет владельца → 403 `not-owner`; в `off` → 404; в `required` с `mu-share-1` → 426 |

Ответ в обоих случаях: `{"<id>": true|false, …}`.

## 6. Коды ошибок

| `code` | Закрытие WebSocket | Когда |
|---|---|---|
| `bad-signature` | 4401 | Подпись не сходится или кадр `auth` неверного формата |
| `id-format` | 4400 | Хост с ключом на 6-значном ID; зритель v2 с `viewer` не из 10 цифр. Повторный `auth` тоже закрывается 4400, но без `error` |
| `id-claimed` | 4403 | ID закреплён за другим ключом (хосту). HTTP 409 legacy-хосту |
| `auth-timeout` | 4408 | Нет `auth` за 10 с |
| `replaced` | 4409 | Подключился хост с ключом владельца: прежнее окно того же ключа (с `error`) или хост без ключа (без `error`); также старый неаутентифицированный сокет хоста с того же IP |
| `rate-limited` | 4429 / HTTP 429 | Лимиты §7; вытеснение неаутентифицированного сокета (самого старого в комнате; у зрителя — также самого старого с этого IP); пауза после отказа. Квота привязок ведущего не касается: у зрителя исчерпанная квота даёт `idVerified:false`, а не ошибку |

HTTP до апгрейда WebSocket:
- 403 — нет токена;
- 426 — `mu-share-1` в `required` или не WebSocket;
- 409 — комната занята (legacy) или `id-claimed`;
- 404 — у зрителя нет трансляции;
- 429 — лимиты.

## 7. Лимиты (фактические значения)

| Что | Значение | Где |
|---|---|---|
| Подключения `/room/*` по IP | 30 / 60 с | `RL_CONNECT` в `wrangler.toml`, до входа в комнату |
| `/status` по IP | 30 / 60 с | `RL_STATUS` |
| `POST /status` по ключу | 6 / мин, считается **после** проверки подписи | `STATUS_PER_KEY_PER_MIN`, в памяти Worker (приблизительно) |
| Сокеты до проверки ключа (хост и зритель отдельно) | 5 в комнате (`MAX_UNAUTH`); лишний вытесняет самого старого. Сокеты, уже приславшие `auth` (идёт проверка), вытесняются **последними** | `limits.js` |
| …с одного IP | Хост — 1 (`MAX_UNAUTH_PER_IP`): новый вытесняет старый (`replaced`). Зритель — 3 (`MAX_UNAUTH_VIEWERS_PER_IP`): четвёртый вытесняет самого старого с этого IP (`rate-limited`); если все три уже проходят проверку — 429 | `limits.js` |
| Ожидающие ответа ведущего (legacy и v2 после ключа) | 10 в комнате (`MAX_PENDING`), 4 с IP (`MAX_PENDING_PER_IP`) | `limits.js` |
| Одобренные зрители | 10 (`MAX_VIEWERS`) | `index.js` |
| Запросы ведущему | 20 / мин (`REQUESTS_PER_MIN`); остальные ждут в очереди и уходят по будильнику; окно «сам себе» без очереди | `index.js` |
| Время на `auth` | 10 с (`AUTH_TIMEOUT_MS`) | `limits.js` |
| Пауза после отказа | 60 с, после третьего отказа подряд — 10 мин; серия сбрасывается через 10 мин без отказов. Ключ — `pub` (v2) или IP (legacy). Проверяется **до** закрепления ID | `DECLINE_BASE_MS`, `DECLINE_LONG_MS` |
| Новые закрепления ID **зрителя** | 20 / сутки на IP (`CLAIM_PER_IP_PER_DAY`), счётчик в storage комнаты `__limits`. Сверх квоты и при сбое счётчика — `idVerified:false`, подключение продолжается | `limits.js`, `index.js` |
| Закрепление ID **ведущего** | Квоты нет: за офисным NAT и мобильным CGNAT новые Mac иначе не начали бы трансляцию | `index.js` |
| Сообщения от зрителя | 20/с, всплеск 40 | token bucket, `index.js` |
| Владелец ID | Освобождается через 180 дней без активности (`OWNER_TTL_MS`); `lastSeenAt` обновляется не чаще раза в час | `index.js` |
| Grace ведущего | 45 с; таймаут молчащего хоста и зрителя — 120 с | `index.js` |

Все лимиты по IP считаются по `ipKey`: IPv4 целиком, IPv6 по префиксу /64. Клиентский `x-relay-ip` всегда перезаписывается значением `CF-Connecting-IP`.

## 8. `AUTH_MODE` и как его переключать

| Режим | Поведение |
|---|---|
| `off` | Аварийный откат. `mu-share-2` обслуживается как legacy: хосту сразу `{"type":"authed","v":2,"mode":"off"}`, зрителю `waiting` без challenge, владельцы не проверяются (но не стираются), `POST /status` → 404 |
| `optional` | По умолчанию и для любого неизвестного значения. `mu-share-2` проходит проверку, `mu-share-1` работает (кроме legacy-хоста на ID с владельцем → 409) |
| `required` | `mu-share-1` → 426 на `/room/*`, `GET /status` и `POST /status`. В `/version` только `mu-share-2` |

Переключение — `[vars] AUTH_MODE` в `relay/wrangler.toml` и деплой. Код не меняется, данные (владельцы ID, квота) сохраняются:
```
cd relay
npm test
npx wrangler deploy --var RELAY_COMMIT:$(git rev-parse --short HEAD)
```
Для разовой смены без правки файла: `npx wrangler deploy --var AUTH_MODE:off` (до следующего обычного деплоя).
`RELAY_COMMIT` relay показывает в `/version`. В скрипт `npm run deploy` он пока не встроен, передавать руками.

## 9. Порядок выката

1. **Relay** (код v2, страница, `AUTH_MODE = "optional"`).
   - Проверить `GET /version`: `protocols` с обоими токенами, `auth: optional`.
   - Старые клиенты работают как раньше; страница для Windows без ключа идёт по старому пути.
2. **Mac, линия 1.5** — обычный релиз через `main`. Автообновление разносит его за ~6 часов. Mac включает `mu-share-2` только по `/version`.
3. **Windows (W1)** — релиз `windows-latest`. Обязательное условие W1: заголовок `mu-share-2` ставится только после `GET /version` с `mu-share-2` в `protocols`.

Нарушать порядок нельзя:
- клиент с `mu-share-2` на relay до v2 получает 403 на всё;
- Mac защищён проверкой `/version`, Windows должен быть защищён так же.

## 10. Критерии перехода в `required`

Все условия сразу (VERSIONING §3 + `.audit/auth-design.md` §5.3):
- прошло ≥ 30 дней после релиза **и** Mac, и Windows с `mu-share-2`;
- после этого вышел ещё один релиз обоих клиентов;
- legacy-подключений меньше 1 % за последние 14 дней.

Последнее условие **пока нечем измерить**: relay не пишет метрик подключений по токенам. До перехода нужно добавить счётчик (например, `console.log({role, token, auth})` + Workers Logs или Analytics Engine).

`required` равносилен удалению `mu-share-1` из принимаемых токенов. Это допустимо только по этим критериям, иначе это бамп MAJOR (VERSIONING §3).

## 11. Откат

**Быстрый (рекомендуемый): `AUTH_MODE=off`.**
- Клиенты v2 продолжают работать: Mac и страница принимают `authed mode:"off"` и отсутствие challenge.
- Владельцы ID в storage сохраняются и снова действуют после возврата в `optional`.

**Откат кода relay на версию до v2** (`wrangler rollback`):
- Старый relay принимает только `mu-share-1` и на `mu-share-2` отвечает 403 на всё, включая страницу.
- Mac 1.5 получает 403, сбрасывает кэш `/version`, заново узнаёт возможности relay и переподключается по `mu-share-1`: ведущий сразу, зритель со второй попытки (с текстом «попробуйте ещё раз»). Перезапуск не нужен.
- Всё равно сначала пробуйте `AUTH_MODE=off`, откат кода — только если сломан сам код.
- Windows-клиенты с W1 (если `/version` проверяется при каждой загрузке страницы) переходят на `mu-share-1` сами.
- Данные Durable Objects (`owner`, `q:*`) старый код игнорирует. При повторном деплое v2 они снова в силе. Владельцев не стирать.
- Миграции DO (`[[migrations]]` в `wrangler.toml`) этой волной не менялись: откат кода их не затрагивает.
