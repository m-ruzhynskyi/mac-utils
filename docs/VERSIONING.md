# Версии Mac Utils

Политика обязательна для людей и агентов. Если код расходится с этим файлом, неправ код: исправляйте его или меняйте политику отдельным PR.

## 1. Mac-приложение

### Формат

| Что | Формат | Пример |
|---|---|---|
| `CFBundleShortVersionString` | `MAJOR.MINOR.PATCH`, только цифры | `1.4.3` |
| `CFBundleVersion` | `MAJOR·1 000 000 + MINOR·1 000 + PATCH` | `1004003` |
| Тег и релиз GitHub | `v` + версия, строго `^v\d+\.\d+\.\d+$` | `v1.4.3` |
| Ассет релиза | `MacUtils.zip` | |

Суффиксы (`-beta`, `+sha`) в этих трёх полях запрещены. Установленные копии до 1.3.100 включительно сравнивают версии старым кодом: он режет строку по точкам и превращает всё нецифровое в 0. Поэтому `v1.4.0-beta.1` для него «новее» `1.4.0`.

`CFBundleVersion` вычисляется из версии, а не из истории git. Он растёт вместе с версией и не зависит от веток и merge-коммитов. Ограничения: `MINOR ≤ 999`, `PATCH ≤ 999`, сборка проверяет это и падает.

### Кто что меняет

- **Единственный источник истины для `MAJOR.MINOR`** — `Resources/Info.plist`, ключ `CFBundleShortVersionString`, значение вида `X.Y.0`. Третья цифра в файле всегда `0`, `CFBundleVersion` в файле не важен: сборка перезаписывает оба.
- **MAJOR** (вручную, только с согласия владельца репозитория):
  - несовместимая смена минимальной macOS;
  - потеря или миграция пользовательских данных и настроек;
  - смена подписи или bundle ID;
  - любое изменение, после которого старые версии не могут обновиться автоматически.
- **MINOR** (вручную, в PR в `development`): набор заметных пользователю изменений, о которых показываем «Что нового». В том же PR обязательно:
  - запись `Release(version: "X.Y", …)` в `Changelog.releases` (`UI/WhatsNew.swift`);
  - `PATCH` в Info.plist остаётся `0`.
- **PATCH** — только автоматически, в CI при релизе: `наибольший PATCH среди тегов vX.Y.* + 1`, или `0`, если тегов линии `X.Y` нет. Номера идут подряд, без пропусков. Руками PATCH не ставится никогда.

### Релизы

- Релиз — это каждый push в `main` (merge PR из `development`) с зелёными тестами. Его делает задача `release` в `.github/workflows/build.yml` командой `MU_RELEASE=1 ./build.sh --universal`.
  - Тесты второй раз не гоняются, если дерево merge-коммита (`HEAD^{tree}`) уже прошло все тесты в прогоне этого PR (задача `tested-tree`). Не доказано — тесты идут как обычно.
- Публикуем только подписанные сборки «Mac Utils Signing» с каналом `release` (см. ниже).
- Релизы идут одной линией. Нельзя выпускать версию ниже уже выпущенной (бэкпорты, хотфиксы старой линии): старые клиенты (≤ 1.3.100) берут из списка релизов **самый свежий по дате**, новые — **наибольший номер**; оба правила запрещают бэкпорты. `version.sh` в release-режиме отказывается собирать коммит, не содержащий последний выпущенный тег.
- Если в `main` быстро влить несколько PR, GitHub оставляет в очереди `release` только последний запуск, промежуточные отменяются без релиза. Это нормально: следующий релиз содержит их изменения.
- Тег `v*` не переиспользуется и не удаляется. При перезапуске упавшего релиза для того же коммита используется уже созданный тег, если он есть.
- Бета-сборки, если понадобятся: тег `vX.Y.Z-beta.N` **только** с флагом pre-release. Updater пропускает pre-release и в старых, и в новых версиях.

### Локальные и dev-сборки

`./build.sh` без `MU_RELEASE=1` собирает dev-сборку:

- версия равна наибольшему тегу `vX.Y.*` текущей линии из Info.plist, а если тегов нет — `X.Y.0`;
- `CFBundleVersion` вычисляется по той же формуле.

Dev-сборка **никогда не новее** релиза, из которого могла бы получиться, и никогда не изображает следующий релиз. Если тегов локально нет (`git fetch --tags` не делали), версия получится меньше настоящей. Это безопасно: Updater предложит обновление, но сам его не поставит.

Дополнительные ключи в `Info.plist` собранного бандла:

| Ключ | Release | Dev |
|---|---|---|
| `MUReleaseChannel` | `release` | `dev` |
| `MUGitCommit` | короткий SHA | короткий SHA, `-dirty` при незакоммиченных правках |
| `MUCommitsSinceRelease` | `0` | число коммитов после коммита тега (или `?`) |

Updater в dev-сборке и в запуске без бандла (нет `MUReleaseChannel`) **ничего не ставит сам**. Он показывает «Доступна X.Y.Z», установка только по кнопке. В интерфейсе dev-версия выглядит как `1.4.3 · dev abc1234+12`.

## 2. Mac Utils Share для Windows (ветка `windows`)

- Отдельная линейка, со своим номером: `MAJOR.MINOR` берётся из `windows/package.json` (меняется вручную, по тем же правилам, PATCH там всегда `0`), `PATCH` = `github.run_number` workflow `windows.yml`, растёт сам и при смене линии не сбрасывается. Неверный формат версии в `package.json` останавливает сборку.
  - История: до W1 сборки шли как `1.0.<run>` (последняя 1.0.11). С W1 (ключ устройства, `mu-share-2`) — линия 1.1 (W1 временно откачен, см. ниже).
- В `windows.yml` перед сборкой есть шаг `npm test --if-present`. Сейчас тестов у клиента нет (они ушли вместе с откатом W1 в 1.1.13), шаг ничего не делает. Когда тесты вернутся вместе с W1, в `package.json` снова появится скрипт `test`, и упавшие тесты остановят релиз.
  - 1.1.13: W1 откачен (на Windows перестали работать кнопки страницы, причина не найдена без машины с Windows). 1.1.14: окно без фонового замедления, свёрнутое приложение держит 30 к/с.
- Публикация — только в перезаписываемый pre-release `windows-latest`. Теги Windows-клиента **никогда не начинают с `v`**: Mac-Updater отбирает релизы по `v`.
- Совместимость с Mac-версией обеспечивает только протокол share (раздел 3), номера версий у них не связаны.

## 3. Протокол трансляции `mu-share-N` и relay

- `mu-share-N` — версия протокола. Её шлют клиенты в заголовке `X-MacUtils-Client`, а relay принимает только известные значения (`ACCEPTED_CLIENTS` в `relay/src/index.js`).
- **Сейчас:** relay принимает `mu-share-1` (без ключей) и `mu-share-2` (проверка устройства ключом Ed25519, протокол v2: [SHARE-PROTOCOL.md](SHARE-PROTOCOL.md)).
  - Клиент ставит `mu-share-2` только если relay объявил его в `GET /version` → `protocols`; иначе `mu-share-1`.
  - Mac так делает с линии 1.5; Windows обязан так делать с задачи W1.
- **Без бампа (обычный случай):** только добавочные изменения. Новые поля и новые `type` сообщений можно добавлять; неизвестное получатель обязан игнорировать. Старый клиент должен продолжать работать с новым.
- **Бамп `N → N+1`:** только при несовместимом изменении (формат бинарных кадров, рукопожатие, смысл существующих полей). Порядок строго такой:
  1. relay принимает **оба** токена, задеплоить (набор `ACCEPTED_CLIENTS` и `GET /version` есть: задача V8 сделана в волне аутентификации share);
  2. выпустить Mac-релиз и Windows-сборку с `mu-share-N+1`;
  3. старый токен убрать не раньше чем через 30 дней после шага 2 и после ещё одного релиза обоих клиентов.
- Бамп протокола, ломающий связь со старыми клиентами без шага 1, — это бамп **MAJOR** Mac-приложения.
- **Удаление `mu-share-1`** = режим `AUTH_MODE = "required"` на relay. Условия, все сразу:
  - прошло ≥ 30 дней после релиза Mac **и** Windows с `mu-share-2`;
  - после этого вышел ещё один релиз обоих клиентов;
  - legacy-подключений < 1 % за 14 дней.

  Для последнего условия relay сначала должен научиться считать подключения по токенам, сейчас метрики нет. Подробно — [SHARE-PROTOCOL.md](SHARE-PROTOCOL.md), разделы 8–11.
- **Relay-воркер** не имеет semver. Его версия — коммит, из которого он задеплоен:
  - деплой только из чистого дерева, закоммиченного в `main` или `development`, после `npm test --prefix relay`;
  - деплой с `--var RELAY_COMMIT:<короткий SHA>`: relay отдаёт его в `GET /version` вместе со списком принимаемых протоколов и режимом `auth` (V8 сделана; в `npm run deploy` переменная пока не встроена — передавать руками);
  - миграции Durable Objects (`[[migrations]] tag = "vN"` в `wrangler.toml`) — это не версии приложения, их нумерация отдельная.

## 4. «Что нового», заметки релиза, README

- **MINOR/MAJOR:** новая запись в `Changelog.releases` (версия `X.Y`, дата, пункты). Без неё окно «Что нового» не откроется: оно показывается один раз на каждую новую линию `X.Y`, у которой есть запись. Это проверяет тест.
- **PATCH:** запись в Changelog не обязательна. Заметные исправления можно дописать пунктами в запись текущей линии. Заметки релиза на GitHub генерируются автоматически (`--generate-notes`).
- **README** не содержит конкретных номеров версий, только ссылку на этот файл. Номер версии в README всегда устаревает.

## 5. Чеклист: как выпустить версию

1. Работа идёт в `development`. Номера версий руками не трогать.
2. Нужна новая линия (MINOR/MAJOR)? В том же PR:
   - `Resources/Info.plist` → `X.Y.0`;
   - запись `X.Y` в `Changelog.releases`.
3. Менялся протокол share? Сначала relay с двумя токенами (раздел 3), потом клиенты.
4. PR `development → main`, зелёные тесты, merge.
5. CI сам:
   - вычисляет `vX.Y.Z`;
   - собирает и подписывает;
   - проверяет подпись, канал `release`, формат тега, отсутствие тега;
   - публикует релиз.
6. Проверить на странице релизов: тег `vX.Y.Z`, ассет `MacUtils.zip`, не pre-release.
7. Ничего не делать с тегами руками: не создавать, не двигать, не удалять.
   - Это закреплено правилом репозитория «Release tags v*» (ruleset 25226895): изменить, переписать или удалить тег `v*` может только администратор (для ручной уборки после сбоя). Создание не закрыто: в личном репозитории GitHub не даёт сделать исключение для GitHub Actions, а тег создаёт CI.
